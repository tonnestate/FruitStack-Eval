# OGI-013-COLLAB-1 — AMENDMENT-1 (prospective; dated 2026-10-29; no COLLAB-1 episode has been run)

The original design (`evidence/ogi013-phase2/COLLAB_STUDY_DESIGN.md`, `STUDY_LOCK.txt`, `study_manifest.json` v1) is preserved unchanged. This amendment supersedes only what is listed here; `AMENDMENT_LOCK.txt` hashes the resulting files.
Population (48 tasks), conditions (SINGLE, COLLAB, SINGLE-E), seed, strata, the Holm family size (3) and the test (exact two-sided McNemar) are unchanged.

## A. Decision-quality evaluation (`decision_metrics.py`, rewritten; evaluator-only)
- **Attempted vs executed** actions are separated: attempts are the draft/final actions of the review trail; executed actions are the agent's tool calls in the OFFICIAL result paired with their tool messages (`error` flag).
- **Deviation from the reference is not a policy violation.** The official grader for these tasks (reward basis DB/COMMUNICATE) does not evaluate the NL policy assertions, so policy compliance is reported as `NOT_EVALUATED_BY_OFFICIAL_GRADER` unless `nl_assertions` is present.
  What is measured: `state_changing_deviations` (a write executed successfully that the reference does not contain; DB evidence `db_match` reported beside it), `failed_write_attempts`, `unnecessary_transfer`, and the objectives completed / abandoned with a mechanical cause (`TRANSFER`, `PREMATURE_STOP_PENDING`, `OTHER_TERMINATION`).
- Review outcomes: PREVENTED_WRITE_ERROR, ERROR_REPLACED_BY_DIFFERENT_ERROR, ERROR_NOT_FIXED, CORRECT_BLOCKED, VALIDATED_CORRECT, UNNECESSARY_CHANGE, NO_CHANGE_SAFE.
- **E3 is redefined** from "≥ 1 unexpected write or unexpected transfer executed" to **"no state-changing deviation"** (the episode executed no write that succeeded although the reference does not contain it), COLLAB vs SINGLE, exact two-sided McNemar on pairs where both episodes have an official result (others excluded and counted). Transfers are reported separately and descriptively.
  Reason: PILOT-4 showed that a transfer is a different failure from a state change and the original E3 mixed them; the reference is a benchmark artefact, not a policy judgement.
- **Isolation:** the reference actions are read only by the evaluator (`analyze_study.py`, `decision_metrics.py`). No file under `runners/` mentions `evaluation_criteria` or imports the metrics (a test enforces this); the agent receives the tau2 `task` object but reads only its id.

## H. Credential-health carry-forward (2026-10-29, before any COLLAB-1 episode completed; root-cause correction of the repeated exhausted-Groq waits)
Root cause (verified in PlumMe's code and the episode state files): PlumMe stores credential health (billing disablement, cooldowns, failure counts) in the state directory of ONE process; every episode has its own, so an exhausted credential looked healthy to the next episode, the next block attempt and the next simulator selection, and PlumMe resets the billing counters when a window expires, so the same 600 s cooldown repeated. The operator-terminated attempt wrote no exhaustion row, and `sim_exhausted.jsonl` was keyed by model only (a global blacklist even when another provider could serve the model) and consulted only when an allowlist existed.
Correction (PlumMe's routing unchanged; active only in campaigns - `OGI013_PILOT_RUNS` set; the frozen conditions never set it): `runners/ogi013_credential_health.py` merges every earlier episode's credential health (finished, failed, interrupted, archived) into `<runs>/credential_health.json` and seeds each new episode's `credential_sources.json` with it; billing exhaustion is sticky and escalating (re-disabled until last failure + PlumMe's own `backoff_s("billing", events)`: 10 min, 20, 40 ... 24 h; only a success resets the count). `ogi013_sim_supply._selection_pool` now excludes a model only when every provider that can serve it is exhausted (rows record the exhausted providers); without an allowlist PlumMe's BEST already never sees an exhausted credential because the health is seeded. The block keeps one simulator model across SINGLE, COLLAB and SINGLE-E. Tests: `tests/test_ogi013_credential_health.py` (the recorded sequence with PlumMe's real credential broker). File hashes: `AMENDMENT_LOCK.txt`.

## I. Objectives are the expected state-changing actions (2026-10-29; evaluator-only correction, made before any outcome analysis; one raw episode result, `airline:7` SINGLE reward 0.0, existed and has not been analysed)
The acceptance campaign showed that `decision_metrics` counted expected READ actions (lookups, searches) as objectives, so an episode that completed every write was reported as having abandoned objectives. Objectives are now the expected WRITE actions of the reference (`expected_writes`); `expected_actions_completed` / `objectives_abandoned` / `abandon_cause` refer to them; the full reference list remains in `expected_actions`. No agent code is affected (the reference is read only by the evaluator).

## J. Exhausted credentials: renewal-cycle recovery, zero waiting (2026-10-29, owner corrections; supersedes the wait/window parts of G and H)
Defect in G/H: a bounded wait (120 s) and escalating billing windows (10/20/40 min) are timers. Corrected, in the existing credential-health layer (PlumMe's routing untouched, no new subsystem):
- `BILLING_OR_CREDIT_EXHAUSTED` marks the credential **EXHAUSTED** at once (in-process latch + registry), persisted across processes, episodes and restarts. No 600 s cooldown, no exponential ladder; no timer ever makes it healthy.
- Recovery follows the **renewal cycle** from explicit configuration `runs/credential_renewal_policy.json` (by handle or provider: DAILY / WEEKLY / MONTHLY with a known `reset_at` / UNKNOWN). UNKNOWN or non-renewing = never retried automatically (the default; nothing is assumed about any provider). At most **one availability probe per cycle** (the first real request of one episode); success restores AVAILABLE, failure restores EXHAUSTED until the next cycle; an unused probe is released, not spent. Operator renewal is also positive evidence. Persisted: reason, policy, next probe time, last probe result; failure kinds (exhausted credit / rate limit / auth / network) are kept apart and only the first is sticky.
- The simulator layer **never sleeps**: `OGI013_SIM_MAX_WAIT_S`/`MAX_WAIT_S` are removed. A failed call moves at once to the next eligible route/model; a pinned model with no eligible route ends the attempt immediately (`SIM_ROUTE_FAILED`, whole-block discard, a fresh block selects another model; the three conditions of a block still share one simulator model); no eligible model at all ends with `SIM_ROUTE_FAILED:SUPPLY_UNAVAILABLE` immediately. Model selection excludes a model only if every provider serving it is exhausted in the registry, never by a clock; `sim_exhausted.jsonl` is evidence only.
Scientific conditions (tasks, arms, order, budgets, metrics) are unchanged. Hashes: `AMENDMENT_LOCK.txt`.

## K. Simulator supply starvation does not consume block attempts (2026-10-29, after 13 blocks were scored INFRA_INCOMPLETE within minutes)
Measured: with zero-wait selection (J), a period in which every allowlisted simulator route was rate limited/exhausted (kilo-gateway RATE_LIMITED on all its models, Groq/Google EXHAUSTED, OpenRouter limited) ended each block attempt in ~22 s, so blocks airline:12/14/17/20/21/23/33/39/40/42 and retail:0/11/15 used their 3 attempts without a single simulator answer. That is a supply outage, not a pinned simulator route that failed during a block. Change: a failure at block START where no allowlisted model answered is `SIM_ROUTE_FAILED:SUPPLY_UNAVAILABLE`; the launcher archives the attempt as evidence (`discarded/<task>-supply<ts>`), logs `SUPPLY_UNAVAILABLE` at once, consumes NO attempt, defers the block to the back of the queue and tries the next block; a full pass without supply is logged and re-checked after 20 s (PlumMe's eligibility decides, no credit reset is awaited). A pinned model that fails DURING a block still counts as one of the 3 attempts (registered rule). The 13 starved blocks were reinstated (their markers/attempt directories renamed `*reinstated-supply-starved*` / `*-supply-attemptN`, nothing deleted); completed blocks (airline:7, 11, 15) and their episodes are untouched.
Addendum to K (same day): eligibility is not capacity (PlumMe listed kilo-gateway routes as eligible that answered RATE_LIMITED in 0.2 s). Before a block is STARTED the launcher now runs `supply_gate.py`: one real, tiny, zero-cash completion through PlumMe on allowlisted models until one answers; that model is written as the block's pinned simulator model. If none answers, nothing is started, no task or attempt is consumed, `SUPPLY_UNAVAILABLE` is logged and the same block waits at the front of the queue (re-check every 120 s). `status.py` no longer counts infrastructure-incomplete blocks as progress and reports `SUPPLY_UNAVAILABLE` instead of PROGRESSING. Gate probe requests are logged in `runs/supply_gate.jsonl`.

## S. Simulator allowlist retired; mechanism-sensitive stratum and activation reporting (2026-10-29, prospective; fixed before any further block selection or analysis)
**Allowlist.** The ten-model `sim_allowlist.json` (a capacity survey of 2026-10-27) is not part of the registered protocol (which says PlumMe selects the block's simulator model once; `_single_provider_keys` is the original multi-provider hint). It restricted the whole campaign to ten models, most with a single FreeLLMAPI route, and was a main cause of 20+ lost block attempts today (`SIM_ROUTE_FAILED`). Retired (file kept as `sim_allowlist.json.retired-20261029`). The supply gate now takes PlumMe's BEST selection over ALL executable routes (FreeLLMAPI, pollinations, kilo, openrouter, nvidia, opencode-zen, donors, whatever PlumMe currently sees as eligible), preferring models served by >= 2 providers, verifies the pick with one real request and pins it for the block's three conditions. Objective suitability rule, decided from the model id alone before any episode: the simulator must be a general-purpose chat model (not guard/embed/rerank/moderation/speech/image/uncensored/role-play variants) of >= 20 B parameters where the id states a size (the first unfiltered BEST pick was `qwen3guard-gen-0.6b`, a safety classifier). 
**Mechanism-sensitive stratum (MS), defined from the task definitions only.** MS = registered tasks whose reference solution contains >= 2 state-changing (WRITE) actions (`expected_write_actions >= 2` in the frozen manifest): 19 of the 48 tasks (airline 7, 14, 17, 21, 23, 33, 39, 42; retail 11, 16, 22, 31, 41, 59, 72, 76, 107, 109, 110). These are the tasks with several consequential decisions, i.e. where the reviewed-decision mechanism (every WRITE/TRANSFER is reviewed) has repeated opportunities and where an error-correction or continuity effect can matter. The registered primary analysis (all 48 tasks, intention-to-treat, E1-E3) is unchanged; MS and the activation measures below are SECONDARY and EXPLORATORY.
**Activation reporting.** `results_table.py` reports per episode: reviews run, consequential (WRITE/TRANSFER) reviews, reviews that changed the action. An episode in which COLLAB ran no consequential review is reported as "no organisational opportunity reached" — it is a task-performance outcome of the agent, not evidence for or against the mechanism, and it is never excluded from the primary analysis. No claim of benefit, harm or equivalence is made from episodes without activation.
